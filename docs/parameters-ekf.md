# EKF and Companion Link Parameters

Generated by hand from `apps/param/param.c`, `apps/ekf3/ekf_sources.h` and
`apps/ekf3/ekf_sources.c` on 2026-09-03. The parameter table in `param.c` is
the source of truth; if this disagrees with it, it is this file that is wrong.

`param show EK3_` and `param show EXT_` print the live values and the
descriptions the firmware itself carries.

## EKF aiding source numbers

The numbers match ArduPilot EKF3, so a value copied from an ArduPilot
configuration means here what it means there.

| Value | Name | What it is |
|---|---|---|
| 0 | `NONE` | No aiding. The state is left to inertial propagation. |
| 1 | `BARO_OR_COMPASS` | Barometer for height, magnetometer for yaw. Which one depends on the state it is assigned to. |
| 2 | `RANGE_OR_GPS_YAW` | Rangefinder for height, GPS heading for yaw. |
| 3 | `GPS` | GNSS position and velocity. |
| 4 | `BEACON` | Range beacons. |
| 5 | `OPTICAL_FLOW` | Optical flow. |
| 6 | `EXTERNAL_NAV` | An absolute pose from the companion computer. |
| 7 | `WHEEL` | Wheel odometry. |
| 8 | `GSF_YAW` | Gaussian-sum filter yaw estimate. |

Value 1 and value 2 each mean two different sensors. That is ArduPilot's
convention, not a mistake here: the number is read in the context of the
state it was assigned to, so `POSZ=1` is the barometer and `YAW=1` is the
compass.

## Which numbers each state accepts

Set by `valid_*()` in `apps/ekf3/ekf_sources.c`. A value outside its column is
**refused at startup with a named error**, not clamped - `ekf3 start` reports
which parameter and why, and does not run. `PARAM_RANGE_ENUM` refuses at the
shell too: neighbouring source numbers are unrelated sensors, so coercing one
to another would silently fuse the wrong thing.

| Parameter | Accepts | Meaning |
|---|---|---|
| `EK3_SRCn_POSXY` | 0, 3, 4, 6 | Horizontal position |
| `EK3_SRCn_VELXY` | 0, 3, 5, 6, 7 | Horizontal velocity |
| `EK3_SRCn_POSZ` | 0, 1, 2, 3, 4, 6 | Height |
| `EK3_SRCn_VELZ` | 0, 3, 6 | Vertical velocity |
| `EK3_SRCn_YAW` | 0, 1, 2, 3, 6, 8 | Heading |

Note the parameter's numeric range is only a coarse bound - `VELZ` allows up
to 6 but accepts just three of those values. The validator is the real check.

## What is actually fused today

Naming a source makes a measurement **eligible**. It does not make it exist.
The following sources are wired to fusion:

| Value | State | Status |
|---|---|---|
| 1 | `POSZ` | **Fused.** Barometer height. |
| 1 | `YAW` | **Fused.** Magnetometer heading. |
| 6 | `POSXY` | **Fused.** Companion-computer position. |
| 6 | `YAW` | **Fused.** Companion-computer yaw. |
| 7 | `VELXY` | **Fused.** VESC speed plus the lateral body-velocity constraint. |
| 5 | `VELXY` | Not implemented. This is the DEFAULT and is inert. |
| 2, 3, 4, 8 | any | Not implemented. No driver publishes them. |

`EK3_SRC1_VELXY = 5` names optical flow and fuses nothing, so horizontal
velocity is unaided: it integrates from accelerometers between position
updates. Worth knowing before reading a velocity number.

Each available observation also has an explicit Kalman-gain mask:

- external x/y position can correct horizontal position and velocity only;
  attitude, vertical states and all biases have zero gain;
- wheel odometry can correct horizontal velocity only; attitude, vertical,
  position and bias states have zero gain;
- barometer height can correct vertical position and velocity only; every
  attitude and bias row has zero gain;
- heading corrects rotation and gyro bias only, projected onto the physical
  navigation-up axis so roll and pitch do not move;
- the gravity pseudo-measurement corrects attitude and IMU biases only.

The inertial process model always propagates the complete state. Missing
observations affect fusion and solution-validity flags, not the propagation
equations.

## Source sets

Three complete sets exist; `EK3_SRC_SET` chooses which one is live.

| Parameter | Default | Notes |
|---|---|---|
| `EK3_SRC_SET` | 1 | Which set is active. 1, 2 or 3. |
| `EK3_SRC_OPTIONS` | 0 | Bit 0 fuse all velocities, bit 1 align external nav to flow. |

Defaults per set:

| | POSXY | VELXY | POSZ | VELZ | YAW |
|---|---|---|---|---|---|
| **Set 1** (live) | 0 none | 5 flow | 1 baro | 0 none | 1 compass |
| Set 2 | 6 extnav | 6 extnav | 6 extnav | 6 extnav | 6 extnav |
| Set 3 | 0 none | 0 none | 0 none | 0 none | 0 none |

Set 2 is an all-external-navigation set, but `POSZ=6` and `VELZ=6` and
`VELXY=6` is not implemented - selecting set 2 today gives you external
position and yaw and nothing else, with height unaided. Set `EK3_SRC1_POSXY=6`
and `EK3_SRC1_YAW=6` instead if you want external navigation alongside a
working barometer.

### The two FLOORS

`EK3_EXT_M_NSE` and `EK3_EXT_YAW_NSE` are **minimums, not defaults**. The
noise actually fused is `max(what the source reported, this parameter)`.

A companion claiming millimetre accuracy is therefore fused at 0.10 m until
you lower the parameter. This is ArduPilot's treatment of `posErr` and it is
deliberate: a source should not be able to talk the filter into trusting it
more than the operator configured. `ekf3 status` prints the noise actually
used, so a source under-reporting its error is visible rather than silent.

### Why the yaw noise is loose

`EK3_YAW_M_NSE = 0.5` rad is far looser than a compass's real accuracy. That
is ArduPilot's default and worth keeping: a loose measurement noise makes the
filter lean on the gyro between updates and limits how hard one disturbed
reading can pull the heading. It is the first thing to tune once the path is
proven on hardware.

### Vertical bound and accelerometer bias

`EK3_HGT_LIM` is a safety bound, not a height measurement. It is applied to
both the delayed fusion state and the forward-replayed published state. A
clamp count that keeps increasing means the unconstrained vertical estimate
is wrong; it does not mean the bound has made height observable.

Barometer pressure drift commonly corresponds to much more than 0.1 m. A
tight car-height bound can therefore operate frequently while `POSZ=1` is
selected. Barometer fusion is deliberately unable to update accelerometer
bias: otherwise the position/bias covariance makes pressure drift look like
a persistent body-Z acceleration, and the height clamp discards the position
correction while retaining that false bias. Body-Z accelerometer bias is
learned only from stationary gravity and accepted zero-velocity updates.

### Mocap marker to IMU transform

The external packet describes the mocap marker origin, while strapdown
propagation describes the IMU/body origin. The estimator composes
`T_map_marker * T_marker_body` before datum creation, delay buffering and
innovation calculation. Therefore `EK3_EXT_POS_*` is the vector from the
marker centre to the IMU centre in marker axes; do not enter its negative.
Yaw uncertainty is also propagated through the horizontal lever arm.

The current companion packet is planar (`x`, `y`, `yaw`). Consequently X/Y
translation and relative yaw affect the fused planar pose now. Z translation
and relative roll/pitch are retained in the full 3-D transform, but cannot
affect the present planar observation until the companion protocol supplies
marker Z, roll and pitch.

### Wheel-stop zero velocity

Zero motor ticks do not prove zero chassis velocity during locked-wheel
braking or wheel slip. A zero-velocity update is permitted only after the
wheel threshold and the independent IMU low-dynamics test all pass. The IMU
test includes the configured gravity-deviation and acceleration-variance
limits; with external position active it additionally checks non-gravity
acceleration and estimated horizontal speed. `ekf3 status` prints both live
metrics and the number of blocked wheel-stop fusion attempts.

### Moving wheel odometry

Set the active source set's `EK3_SRCn_VELXY` to 7 only after calibrating
`VESC_SPEED_K`. A value of 1.0 normally still means raw tachometer counts per
second, not metres per second, and would make the observation invalid.
`VESC_STATE_K` is independent and affects only the companion
`VEHICLE_STATE` field; changing it cannot change EKF propagation or wheel
fusion.

At the delayed fusion horizon the VESC speed constrains body-forward velocity.
The body-Z gyro rate and `EK3_WHL_POS_X/Y` translate velocity from the wheel
reference point to the IMU, while vehicle attitude rotates forward/left into
navigation X/Y. No wheel observation directly corrects roll, pitch, Z,
position or IMU biases.

The slip detector differentiates VESC speed and low-pass filters that result
and the gravity-removed body-X IMU acceleration with the same
`EK3_WHL_ACC_TC`. Fusion is skipped while
`|a_wheel| > |a_imu| + EK3_WHL_SLIP`, covering driven wheel spin and
locked-wheel braking without reacting to an unfiltered tick. The ULog
`estimator_diag` topic records both accelerations, wheel innovations/NIS and
accept/reject counters for tuning.

## Frame conventions

Every number above is in the vehicle convention, which is **not** PX4's:

- **Body: +x forward, +y LEFT, +z UP** (FLU)
- **Navigation: East, North, Up** (ENU, ROS REP-103)
- **Yaw is counter-clockwise from EAST**, zero at east, +90 degrees at north

So `position[0]` is east and `position[1]` is north. Roll and yaw run in the
opposite sense to PX4's FRD, because a roll-180 conjugation negates both -
which is also why `SENS_IMU1_ROT` is yaw 90 here where PX4's fmu-v6c uses yaw
270 for the same physical parts.
